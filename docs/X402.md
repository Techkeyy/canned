# Health Guard x402 / B402

Directive #23 pins the official BNB Agent Studio seller surface and adds one bounded Health Guard per-request payment face. This document describes what is implemented and what is intentionally still gated.

## Current contract

- Endpoint: `POST /x402`
- Status: `GET /api/reference/health-factor/x402`
- Protocol: x402 request/response face, settled through the official B402 seller runtime
- Network: BSC Testnet, chain `97`
- Asset: `U`, `0xc70B8741B8B07A6d61E54fd4B20f22Fa648E5565`
- Default price: `0.0005` U
- Directive cap: `0.001` U
- Recipient: the existing Health Guard provider wallet from `reference-provider-wallets`; a configured `CANNED_X402_PAY_TO` must match it exactly, case-insensitively

The paid request body uses the existing deterministic Health Guard task shape:

```json
{
  "prompt": "{\"account\":\"0x...40 hex characters...\",\"protocol\":\"venus\",\"authoritativeSnapshot\":{}}"
}
```

`authoritativeSnapshot` must satisfy the same validation used by the ERC-8183 Health Guard service. An optional `previousSnapshot` may be supplied for change detection. The work hook is read-only and deterministic; it does not sign transactions, move capital, or accept a payer-selected operation.

## Availability states

The status endpoint is the source of truth. With no merchant credentials, it reports `state: "dormant"`, `available: false`, and credential presence as booleans only. `POST /x402` returns `503` with the dormant error. This is intentional: a local scaffold must not pretend to be a public payment challenge.

The official seller requires B402 merchant configuration outside the repository. The accepted environment names are:

- `B402_BASE_URL`
- `B402_CLIENT_ID`
- `B402_ACCESS_TOKEN`
- `B402_PRIVATE_KEY` or `B402_PRIVATE_KEY_B64`

Never commit or paste values for these variables. Binance's developer-account flow separates Sandbox/Testnet and Production accounts; use Sandbox/Testnet for the remaining gate.

## Verification gate before one real payment

The next authorized run is bounded to one BSC Testnet payment at or below `0.001` U. It must preserve the exact challenge and terms, verify network/asset/amount/recipient, confirm the buyer wallet and gas preflight, record the settlement/payment identifier and transaction, independently verify settlement on-chain, and replay the same request to demonstrate rejection. If the public challenge, settlement, independent verification, or replay gate fails, stop without payment.

The implementation does not alter the ERC-8183 seller/provider flow, marketplace third-party adapter claims, Altana evidence, or existing Health Guard identity.
